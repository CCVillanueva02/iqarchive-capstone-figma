# AI Agent Instructions — IQArchive Codebase

# Design System & Viewport Instructions

Always strictly follow the IQArchive Design System and Design Token Specification documented in [`resources/css/token-mapping.md`](file:///c:/Users/janss/Herd/iqarchive/resources/css/token-mapping.md) and declared in [`resources/css/app.css`](file:///c:/Users/janss/Herd/iqarchive/resources/css/app.css).

1. **Centralized Tokens Only:** Always use the centralized utility classes generated by `@theme` in `resources/css/app.css` (primary navy, brand orange, zinc scale, surface tokens, and role-based typography). Do NOT hardcode raw hex colors or arbitrary font sizes.
2. **Tailwind v4 Scale & Syntax:** Follow the continuous linear spacing scale (`scale = px / 4`), standard border-radius tokens, dynamic z-indices, and modern Tailwind v4 syntax conventions defined in `resources/css/token-mapping.md`.
3. **No Arbitrary Bracket Multiples:** Never introduce arbitrary bracket notation `[...]` when an exact canonical utility exists.
4. **Desktop-Only Policy (No Mobile Accommodation):** IQArchive is strictly a desktop workstation application designed for complex accreditation matrices, multi-document evidence inspections, and dense compliance workflows.
   - **No Mobile Layout Accommodation:** Developers and AI agents are **NOT** required to build or maintain mobile responsive layouts. Design solely for desktop/laptop displays ($\ge$ 1024px / `lg`+).
   - **Global Mobile Guard:** On screen widths smaller than desktop threshold (`< 1024px`), the global `<x-mobile-unsupported />` guard renders a dedicated full-screen overlay informing users that mobile viewports are not supported and directing them to switch to a desktop browser.

# Verification Commands

Whenever making style, template, or CSS updates:
1. Build client assets: `cmd /c npm run build`
2. Run test suite: `cmd /c php artisan test`

# Component Reuse Policy

Before creating a new Blade/Livewire component, check for an existing pattern to extend: document chips, sidebar shell, area tabs. Do not duplicate markup for a "new" version of an existing UI pattern — extend or parameterize the existing component.

# Security Documentation Requirement

Every implemented feature must include a short comment or accompanying note explaining the security reasoning behind it (e.g., why a field is encrypted, why a route is gated). AI agents must not skip this even for small changes — this is an explicit capstone requirement.

# Workflow Rules

For any change touching more than one file or an existing working feature: propose the plan/diff first and wait for approval before applying it. Do not run broad refactors or multi-file edits unprompted.

Match existing code style/structure exactly when adding new sections to a file (migrations, seeders, components).
Prefer extending existing patterns over introducing new libraries or architectural approaches without discussion.

# File Size & Modular Splitting Rule

Avoid generating or maintaining single files that are excessively long (e.g., > 150-200 lines for Blade templates/views).
 
Always proactively splice large views, templates, and components into clean, dedicated partial files (e.g. `partials/stats-bar.blade.php`, `partials/filter-bar.blade.php`, `partials/modals.blade.php`). When creating new features or refactoring existing pages, break them into modular sub-files from the start.
